01. Язык C#: фундамент

Знать не определения, а семантику, копирование, равенство и время жизни значений.

P0

Value type vs reference type

Тип значения (struct, int, enum) хранит само значение; при присваивании обычно копируется. Ссылочный тип (class, массив, делегат, string) хранит ссылку на объект; при присваивании копируется ссылка. «struct всегда на стеке» — неправда. Если структура — поле экземпляра класса, её данные находятся непосредственно внутри этого объекта (обычно в управляемой куче), без boxing. Локальное значение может находиться на стеке, в регистре или оптимизироваться JIT. Boxing — отдельная операция, например преобразование структуры к object или реализуемому интерфейсу, при которой обычно создаётся самостоятельный объект с копией значения.

C#
var a = new Box { Value = 1 };
var b = a; b.Value = 9;               // a.Value == 9: копия ссылки

var p1 = new Point { X = 1 };
var p2 = p1; p2.X = 9;               // p1.X == 1: копия значения

var holder = new Holder();
holder.Position.X = 5;               // поле struct внутри Holder: boxing нет
object boxed = holder.Position;      // boxing: отдельная копия Point
holder.Position.X = 7;               // ((Point)boxed).X всё ещё 5

class Box { public int Value; }
struct Point { public int X; }
class Holder { public Point Position; }

Передача параметров и boxing

  • ref — работа с исходной переменной, обязательна инициализация до вызова; out — метод должен присвоить значение; in — readonly-передача по ссылке (защитные копии у некоторых структур возможны).
  • Без ref даже ссылочный объект передаётся по значению ссылки: изменение его свойств видно, замена локальной ссылки — нет.
  • Boxing — упаковка value type в отдельный ссылочный объект (object o = 42), обычно с выделением памяти и копированием значения; размещение поля struct внутри класса само по себе не boxing. Unboxing проверяет тип и позволяет получить значение (при обычном приведении оно копируется). List<int> обычно обходится без boxing элементов.

Равенство, null, неизменяемость

== — оператор, поведение зависит от типа и перегрузок; Equals — логическое равенство по реализации; ReferenceEquals — тождество ссылок. При переопределении Equals нужно согласованно переопределить GetHashCode. string неизменяем; StringBuilder удобен для множества изменений. Nullable reference types — прежде всего анализ компилятора, а не запрет null на уровне CLR.

Generics, делегаты, LINQ

  • Generics дают статическую типизацию, переиспользование и помогают избежать boxing; ограничения: where T : class/struct/new()/interface. out T (ковариантность) — только выход, in T (контравариантность) — только вход, для интерфейсов/делегатов.
  • Делегат — типизированная ссылка на метод(ы). event ограничивает внешнему коду вызов и замену подписчиков. Подписка на событие долгоживущего объекта может удерживать подписчика от GC.
  • Closure захватывает переменную, не снимок значения; компилятор может создать дополнительный объект с состоянием.
  • IEnumerable<T> — обход; IEnumerator<T> — текущий курсор. yield return реализован state machine. Многие LINQ-операторы ленивые: запрос выполнится при перечислении, возможны повторные вычисления. ToList() материализует.
C#
int x = 1;
Action print = () => Console.WriteLine(x);
x = 5; print(); // 5: захватили переменную, а не 1

var query = numbers.Where(n => n > 0); // ещё не выполнен
var snapshot = query.ToList();           // выполняем сейчас

Ковариантность и контравариантность — направление совместимости типов

Проблема: если Dog : Animal, можно ли использовать Something<Dog> там, где ждут Something<Animal>? Не всегда. Это зависит от объявления параметра типа у обобщённого интерфейса или делегата.

ВидНаправление присваиванияПочему безопасно
Ковариантность out TIEnumerable<Dog> → IEnumerable<Animal>Источник выдаёт Dog, а получить Animal всегда допустимо. Производитель / чтение.
Контравариантность in TIComparer<Animal> → IComparer<Dog>Код, умеющий принимать любого Animal, сможет принять и Dog. Потребитель / аргумент.
Инвариантность TList<Dog> ↛ List<Animal>Изменяемый список и читает, и принимает T: иначе в список собак можно было бы добавить кошку.

Мнемоника: out — отдаёт T, движение от наследника к базовому; in — принимает T, движение от базового к наследнику. Эти ключевые слова в объявлении generic-типа — не то же самое, что модификаторы in/out параметров метода (readonly-ссылка / выходной параметр).

C#
using System;
using System.Collections.Generic;

class Animal { public string Name { get; set; } = ""; }
sealed class Dog : Animal { }

// Ковариантность: IEnumerable<out T>, Func<out TResult>
IEnumerable<Dog> dogs = new List<Dog> { new Dog { Name = "Rex" } };
IEnumerable<Animal> animals = dogs;  // OK: Dog -> Animal

Func<Dog> makeDog = () => new Dog();
Func<Animal> makeAnimal = makeDog;   // OK: результат становится более общим

// Контравариантность: IComparer<in T>, Action<in T>
Action<Animal> logAnimal = a => Console.WriteLine(a.Name);
Action<Dog> logDog = logAnimal;      // OK: метод умеет принять Dog

IComparer<Animal> compareAny = Comparer<Animal>.Create(
    (a, b) => string.CompareOrdinal(a.Name, b.Name));
IComparer<Dog> compareDogs = compareAny; // OK

// Инвариантность: List<T> не объявлен как out/in
// List<Animal> list = new List<Dog>(); // ОШИБКА компиляции

Как объявить свой вариантный интерфейс

C#
interface ISource<out T>  // T только в допустимых выходных позициях
{
    T Read();
    // void Write(T item);  // Ошибка: T нельзя принимать как вход
}

interface ISink<in T>    // T только в допустимых входных позициях
{
    void Write(T item);
    // T Read();             // Ошибка: T нельзя возвращать
}

interface IConverter<in TInput, out TOutput>
{
    TOutput Convert(TInput value);
}

Границы: вариантными параметрами объявляют интерфейсы и делегаты, но не классы (List<T> инвариантен). Вариантные преобразования работают для ссылочных типов, не для int → object. Вариантный T нельзя использовать в параметре метода с ref/in/out. Правило «только вход / только выход» — удобное базовое объяснение; у вложенных вариантных делегатов есть дополнительные допустимые позиции.

Отдельная ловушка: массивы ковариантны: Animal[] a = new Dog[1] компилируется, но попытка a[0] = new Animal() выбросит ArrayTypeMismatchException. Это не generic variance и не гарантирует безопасность во время компиляции.

УточнениеПочему List<Dog> нельзя присвоить List<Animal>, а IEnumerable<Dog> — можно?+
Потому что List<T> инвариантен: у него есть методы добавления T. Иначе через List<Animal> можно было бы добавить не-собаку в исходный List<Dog>. IEnumerable<out T> только предоставляет значения для чтения, поэтому ковариантность безопасна.
УточнениеПочему Action<Animal> можно присвоить Action<Dog>, но не наоборот?+
Action<in T> контравариантен. Обработчик всех Animal умеет принимать Dog. Обработчик только Dog не может безопасно обработать произвольного Animal.
УточнениеКак сочетаются ковариантность и контравариантность в Func<T, TResult>?+
У Func<in T, out TResult> аргумент T контравариантен, результат TResult ковариантен. Например, Func<Animal, Dog> можно присвоить переменной Func<Dog, Animal>.
УточнениеМожно ли преобразовать IEnumerable<int> в IEnumerable<object>?+
Нет. Несмотря на out T, generic variance работает только с неявными ссылочными преобразованиями. Для int → object нужно boxing; такое преобразование всей коллекции автоматически не делается.
УточнениеЧем in/out в generic-типе отличаются от in/out у параметров метода?+
interface IReader<out T> и IConsumer<in T> описывают вариантность типа и возможные присваивания. void M(in Point p) и bool Try(out Point p) управляют передачей аргументов конкретного метода: readonly по ссылке / обязательное присваивание.
УточнениеМожет ли struct содержать ссылочное поле?+
Да. Структура копируется целиком, но содержащаяся внутри ссылка указывает на тот же объект; глубокого копирования не происходит.
УточнениеЧем отличается метод List<T>.ForEach() от оператора foreach?+

foreach — конструкция языка C#, работающая с типами, поддерживающими перечисление (в том числе через IEnumerable/IEnumerable<T> или подходящий GetEnumerator). List<T>.ForEach(Action<T>) — обычный метод списка, который вызывает переданный делегат для каждого элемента.

var numbers = new List<int> { 1, 2, 3 };

foreach (int x in numbers)
{
    if (x == 2) break; // останавливает цикл
    Console.WriteLine(x);
}

numbers.ForEach(x =>
{
    if (x == 2) return; // только завершает текущий вызов лямбды
    Console.WriteLine(x);
}); // после 2 обработает и 3

На практике: foreach поддерживает break и continue, не требует делегата и применим не только к List<T>. У ForEach нельзя прервать обход оператором break; лямбда с захватом переменных может иметь дополнительные расходы. Оба варианта при изменении структуры того же List<T> во время прохода обычно выбрасывают InvalidOperationException. Предпочтительный выбор для обычной итерации — foreach.

УточнениеЧем IEnumerable отличается от IQueryable?+
IEnumerable выполняет операции в памяти при перечислении; IQueryable хранит выражение, которое провайдер (например EF Core) может перевести в SQL. Не каждый метод C# переводится в SQL.

02. Платформы .NET — объяснение без путаницы

Какая версия откуда появилась, что запускает код и что выбирать для Windows/Linux.

P0

Главная мысль

C# — язык программирования, .NET — платформа, на которой выполняется программа. Платформа включает среду выполнения, сборщик мусора и библиотеки.

Две основные ветки — запомни эту схему

.NET Framework 1.x–4.8.1→старая Windows-ветка
.NET Core 1.0–3.1→.NET 5 → 6 → 7 → 8 → 9 → 10→современная кроссплатформенная ветка

.NET 5+ продолжает .NET Core, а не .NET Framework. Название Core просто убрали.

Тогда что такое Mono и .NET Standard?

  • Mono — ещё одна реализация среды выполнения .NET. Её использовали для Linux, Xamarin и Unity до появления .NET Core. Сегодня Mono также применяется в некоторых мобильных сценариях. Это не версия .NET Core.
  • .NET Standard — не платформа и не runtime, а общий набор API, на которые может рассчитывать библиотека. Позволяет писать общие библиотеки для разных веток. Так, netstandard2.0 поддерживается в .NET Framework 4.8 и современном .NET, а netstandard2.1 — не поддерживается .NET Framework.

Что выбирать в реальном проекте?

  • Новый проект под Windows/Linux: современный .NET + кроссплатформенный UI (например, Avalonia).
  • Старый проект на Framework: продолжать поддерживать или переносить с проверкой зависимостей — простая замена версии не поможет.
  • Linux/Mono из вакансии: понимать запуск старых Mono-приложений. Новому Linux-проекту Mono обычно не нужен.

В файле проекта: net48 — Framework 4.8, net10.0 — .NET 10, net10.0-windows — Windows-специфичные API. WinForms/WPF не работают на Linux в современном .NET.

Как ответить за 20 секунд

Готовый ответ «.NET Framework — старая Windows-ветка. .NET Core — новая кроссплатформенная ветка; начиная с версии 5 называется просто .NET. Mono — отдельная реализация runtime. .NET Standard — общий набор API для совместимых библиотек, а не runtime».
С подвохом.NET 5 — это следующая версия .NET Framework 4.8?+
Нет. .NET 5 — преемник .NET Core 3.1. .NET Framework остаётся отдельной Windows-веткой. Современный .NET работает на нескольких ОС.
С подвохомЧтобы запускать C# в Linux, обязательно нужен Mono?+
Нет. Современный .NET работает в Linux сам по себе (обычно с CoreCLR). Mono важен для понимания старых систем и отдельных сценариев. Возможность запустить приложение также зависит от его зависимостей, например WinForms не станет кроссплатформенным.
С подвохомМожно ли выполнить программу «на .NET Standard»?+
Нет. .NET Standard задаёт общий набор API для библиотек, но сам код не выполняет. Библиотеку запускает приложение на конкретной реализации .NET. Для совместимости с .NET Framework обычно выбирают netstandard2.0, а не netstandard2.1.
С подвохомПриложение WinForms на .NET 10 заработает в Linux?+
Нет, WinForms на современном .NET поддерживается только в Windows. Кроссплатформенность платформы .NET не означает кроссплатформенность любой UI-библиотеки. Для Linux/Windows UI нужны другие решения, например Avalonia.

03. Исполнение C#: CLR, Mono, JIT/AOT и GC

Один связный раздел: как C# исполняется, как управляется память и когда реально запускается сборщик.

P0
Ответ за 20 секунд. Компилятор C# (Roslyn) создаёт IL и метаданные. Среда выполнения CLR/CoreCLR или Mono загружает сборки и управляет выполнением. JIT переводит IL в машинный код по мере необходимости (либо используется предварительная компиляция AOT). GC освобождает недостижимые managed-объекты по собственным условиям запуска.

Как C# становится машинными инструкциями

.cs→Roslyn→IL + metadata (.dll)→Runtime loader→JIT → CPU

Roslyn компилирует C# в промежуточный IL и метаданные. Runtime загружает сборки, разрешает типы, обеспечивает GC, исключения и взаимодействие с ОС. JIT обычно компилирует конкретный метод в машинный код при необходимости (с нюансами предварительно скомпилированного кода). Исполнение IL напрямую CPU невозможно: требуется JIT, AOT или интерпретатор.

Что именно делает JIT

  1. Загрузка типа/метода и проверка корректности IL.
  2. Перевод IL в внутреннее представление, построение control-flow graph.
  3. Оптимизации: inlining, устранение проверок границ в допустимых случаях, devirtualization, constant folding, register allocation и другие.
  4. Генерация инструкций конкретной архитектуры (x64, arm64); при tiered compilation возможна перекомпиляция горячего метода.

Mono — полноценный runtime, а не «переводчик .exe для Linux». Историческая команда mono App.exe запускает совместимую сборку под Mono runtime. Современное кроссплатформенное приложение на net8.0/net10.0 обычно запускается через dotnet App.dll на CoreCLR, без установки Mono. Наличие Mono в вакансии может означать legacy-код, собственные библиотеки или требования совместимости — важно уточнить версию и модель запуска.

C#
// Посмотреть реально используемый runtime (современный .NET)
Console.WriteLine(System.Runtime.InteropServices.RuntimeInformation.FrameworkDescription);
Console.WriteLine(System.Runtime.InteropServices.RuntimeInformation.OSDescription);
Console.WriteLine(System.Runtime.InteropServices.RuntimeInformation.ProcessArchitecture);

// В терминале:
// dotnet --info
// dotnet --list-runtimes
// mono --version      # если установлен классический Mono

Тонкие вопросы о JIT

  • Почему первый вызов медленнее? Может выполняться JIT и загрузка зависимостей, а также прогрев кешей. Проверять бенчмарком с warmup.
  • Почему Release быстрее Debug? Из-за оптимизаций компилятора/JIT и дополнительных механизмов отладки, но измерять нужно одинаковые сборки и среду.
  • А что с generic? CoreCLR может разделять native-код для ссылочных инстанцирований generic и специализировать value-type варианты; это не простое правило «каждый T всегда новый машинный код».
  • Reflection.Emit / dynamic? Совместимость зависит от runtime; NativeAOT, trimming и полное AOT требуют особого внимания.
УточнениеCLR, CoreCLR и Mono — что из них JIT?+
CLR/CoreCLR/Mono — runtime. JIT — механизм компиляции внутри runtime: в CoreCLR обычно RyuJIT, у Mono — свой JIT. Названия не являются взаимозаменяемыми.
УточнениеЕсли есть JIT, зачем AOT?+
Для сокращения затрат на JIT при старте, требований платформ без генерации исполняемого кода во время работы и некоторых deployment-сценариев. Цена — сложность сборки, размер или ограничения динамических функций.
УточнениеДелает ли NativeAOT программу полностью без GC?+
Нет. NativeAOT не использует JIT, но включает необходимую поддержку выполнения, в том числе GC. AOT говорит о времени компиляции, а не об отсутствии управления памятью.
УточнениеКакие ситуации делают performance-бенчмарк нечестным?+
Debug, активный профилировщик, отсутствие прогрева tiered JIT, разные входные данные/CPU governor, некорректное измерение аллокаций, DCE оптимизировал вычисление. Для .NET удобен BenchmarkDotNet с прогревом.

Память в runtime: стек, куча и value types

Стек обычно содержит кадры вызовов и часть локальных значений, но JIT может размещать значения в регистрах и оптимизировать их. Managed heap содержит управляемые объекты. Поле struct внутри класса хранится внутри объекта класса и само по себе не вызывает boxing. Boxing — отдельная операция: упаковка копии value type в объект.

Когда и почему запускается GC?

Не по таймеру и не сразу после выхода переменной из области видимости. Время запуска определяет runtime. Самый частый повод — новые выделения памяти: когда достигнут динамически настраиваемый порог для поколения, запускается подходящая сборка.

УсловиеЧто происходит
Порог выделений памяти достигнутНапример, для молодых объектов исчерпан доступный бюджет Gen 0. Обычно начинается Gen 0 GC. Для больших объектов порог LOH может привести к Gen 2 GC. Пороги адаптивные, не фиксированные «каждые N мегабайт».
В системе мало свободной памятиGC получает сигнал о нехватке памяти от ОС/хоста и может собрать старшие поколения, а также активнее уменьшать занятую кучу.

Точный ответ на собеседовании: GC чаще всего запускается из-за давления аллокаций. Порог зависит от поведения приложения, объёма живых объектов и состояния памяти; дополнительно влияет нехватка памяти на уровне ОС и явные вызовы GC.Collect. Сам факт присваивания null не запускает сборку.

Механизм сборки по шагам

1 · Выделение объектов→2 · Достигнут порог→3 · Найти живые→4 · Освободить мусор→5 · Продолжить работу
  1. Выделение памяти. Для большинства небольших управляемых объектов runtime использует быстрое выделение последовательных участков managed heap. Новые обычные объекты начинают в Gen 0.
  2. Запуск и согласование с потоками. Когда GC нужен доступ к согласованным ссылкам, управляемые потоки достигают safe points, и runtime может их приостановить (Stop-the-World). Это не означает, что все фазы любой сборки всегда выполняются при остановленном приложении.
  3. Поиск корней (GC roots). Ссылки из регистров и стеков активных потоков, статических полей, GC handles и инфраструктуры runtime. По ним GC обходит граф объектов и отмечает достижимые. Это не reference counting: циклы без пути от корней тоже собираются.
  4. Освобождение недостижимых. Объекты, не достижимые из корней, становятся кандидатом на освобождение. Объекты с финализатором могут сначала попадать в очередь финализации и сохраняться до последующей сборки.
  5. Уплотнение там, где это выгодно. GC может переместить выжившие объекты, убрать промежутки, исправить ссылки. Но не всякая сборка уплотняет все области: LOH обычно освобождается без регулярного перемещения больших объектов; закреплённые (pinned) объекты также нельзя двигать.
  6. Завершение. GC обновляет поколения и бюджеты аллокаций, после критических фаз возобновляет работу приложения. При background GC часть работы для Gen 2 идёт параллельно с пользовательскими потоками.
Пример для понимания: создали объекты A → B → C и отдельно D. Переменная ссылается на A. Если нет никаких ссылок от корней к D, он недостижим — даже если D ссылается на себя или образует цикл. A, B и C живы, пока есть достижимый путь.

Поколения: что конкретно собирается?

Идея простая: большинство новых объектов быстро становится мусором, поэтому невыгодно каждый раз просматривать всю кучу.

Stop-the-World и background GC — почему это важно

  • Foreground Gen 0/1 GC: управляемые потоки временно останавливаются на критическую часть сборки. Обычно это сравнительно короткие паузы, но не гарантированная длительность.
  • Background Gen 2 GC: часть длительного обхода выполняется параллельно с работой приложения; короткие остановки всё равно нужны для отдельных фаз. Пока идёт background Gen 2, возможны отдельные foreground Gen 0/1.
  • Workstation GC чаще выбирают для интерактивных приложений с акцентом на отклик. Server GC рассчитан на пропускную способность и использование нескольких GC-потоков/куч; фактическое поведение зависит от конфигурации и ресурсов.

Почему интерфейс иногда «замирает»? На UI-потоке не обязательно должен выполняться код GC. Во время Stop-the-World managed UI-поток тоже приостанавливается, поэтому он временно не обрабатывает сообщения окна.

Почему после GC память процесса может не уменьшиться?

GC освобождает память для будущих управляемых объектов, но не обязан немедленно возвращать всю её операционной системе. У процесса есть несколько различных метрик:

  • Живые managed-объекты: объекты, которые GC считает достижимыми.
  • Размер managed heap: пространство, которое runtime использует для размещения объектов и повторного использования; в нём может быть свободное место.
  • Рабочий набор процесса (working set): физическая память, находящаяся в ОЗУ; туда входят не только managed heap, но также код, стеки, native allocations, библиотеки и другое. «Память процесса» в диспетчере задач — не синоним размера живых объектов.

Например, GC собрал 300 МБ временных объектов, но оставил часть сегментов кучи под будущие выделения. Количество живых managed-объектов уменьшилось, а показания Task Manager могли почти не измениться. Это не обязательно утечка.

Как оптимизировать работу GC на практике

  • Сократить число ненужных аллокаций: избегать создания временных массивов/строк в циклах обработки данных; использовать Span<T>, повторное использование буферов и ArrayPool<T>, когда это оправдано.
  • Не удерживать объекты лишними ссылками: ограничивать кеши, отписываться от долгоживущих событий, освобождать остановленные таймеры, следить за статическими коллекциями.
  • Аккуратно с LOH и pinning: большие массивы увеличивают давление на Gen 2; закреплённые объекты могут затруднять уплотнение. По возможности переиспользовать крупные буферы.
  • Освобождать внешние ресурсы: using/Dispose для соединений, файлов, сокетов и дескрипторов; финализаторы не обеспечивают своевременное закрытие.
  • Сначала измерить: allocation rate, частоту Gen 0/1/2, паузы, heap dump и корни удержания в dotMemory, PerfView, dotnet-counters / dotnet-trace. Не вызывать GC.Collect() «для ускорения».

Дополнительные вопросы с подвохом по GC

УточнениеКогда запускается GC? Есть ли фиксированный интервал?+
Нет фиксированного таймера. Основные три причины: динамический порог выделений памяти (обычно основной), недостаток памяти в системе, явный GC.Collect(). Количество аллокаций и объём выживших объектов влияют на частоту сборок.
УточнениеПочему после сборки мусора объём памяти, занимаемой процессом, не обязательно уменьшается?+
GC может освободить объекты внутри managed heap, сохранив сегменты для последующих аллокаций. Рабочий набор процесса включает также native allocations, стеки, код и другие области. Нужно сравнивать managed heap / live objects, working set и другие метрики, а не ожидать немедленного уменьшения цифры в диспетчере задач.
Хороший вопросВсегда ли GC останавливает все потоки?+
Нет, не на всё время каждой сборки. Во время Stop-the-World фаз managed-потоки приостанавливаются (например, для согласованного обхода корней и перемещения объектов). Background Gen 2 может выполнять значительную часть работы параллельно с приложением, но всё равно имеет короткие паузы; Gen 0/1 foreground-сборки останавливают managed-потоки.
УточнениеПочему сборка Gen 0 не удаляет старый объект из Gen 2?+
Gen 0 GC проверяет только молодое поколение плюс нужные межпоколенные ссылки. Объекты Gen 2 не становятся кандидатами на освобождение до сборки Gen 2, даже если ссылки на них уже исчезли. Поэтому Gen 0 дешевле полной сборки.
УточнениеЧто делают финализатор, Dispose и SafeHandle?+
Dispose — явное своевременное освобождение ресурсов; финализатор выполняется недетерминированно, а объект с финализатором обычно требует дополнительной сборки. SafeHandle предпочтителен для владения native-дескриптором. GC не заменяет using.
УточнениеСколько поколений у GC? LOH — Gen 3?+
Основные логические поколения — 0, 1, 2. LOH иногда называют физическим Gen 3, но собирают его вместе с Gen 2. Не отвечать «4 обычных поколения».
УточнениеЧто будет если вызвать GC.Collect() в каждом цикле?+
Может вызвать частые дорогие сборки, продвижение живых объектов и деградацию. GC настроен эвристически; ручной Collect нужен редко, только по измерениям.

Утечки памяти в .NET: почему GC не спасает

Управляемая утечка — ненужный объект всё ещё достижим из GC Root; для GC он живой. Типичные причины: подписка долгоживущего сервиса на события окна, static-список/словарь, неограниченный кэш, таймер, замыкание с захватом большой структуры, удержанный Task или ссылка из singleton. Неуправляемая утечка — нативная память, дескрипторы файлов, сокеты, bitmap/handle, которые нужно освобождать отдельно.

Как искать утечку или лишние аллокации

  1. Воспроизведи проблему одинаковыми действиями, например 100 раз открыть/закрыть окно.
  2. Сними снимок памяти до и после в dotMemory / Visual Studio Memory Profiler; сравни число объектов и их объём.
  3. Для оставшихся объектов открой retention path до GC Root — кто удерживает ссылку.
  4. Исправь жизненный цикл: отписка, ограничение кэша, освобождение дескриптора, сокращение времени удержания ссылки.
  5. Для CPU и пауз изучи dotTrace, PerfView / dotnet-trace: горячие методы, число аллокаций, время GC. Оптимизируй после измерений.
УточнениеЕсли объект не используется, почему GC его не собирает?+
GC опирается на достижимость из корней, а не на смысловую полезность объекта. Ссылка в статическом словаре или обработчике события удерживает объект.
УточнениеПочему Dispose не заменяет GC?+
Dispose — детерминированный способ освободить ресурсы, особенно нативные. GC отдельно освобождает память недостижимых управляемых объектов.

Dictionary: от ключа до значения

Упрощённая модель Dictionary<K,V> в .NET: buckets + entries + цепочки коллизий
  1. GetHashCode(key) → вычисляем bucket по хешу и размеру массива.
  2. Bucket указывает на первую запись в entries[]. При коллизии идём по связям next.
  3. Проверяем хеш и Equals. Совпавшие хеши не означают равные ключи.
  4. При росте коллекции увеличивается вместимость и переорганизуются buckets; операция вставки тогда дорогая, средняя амортизированная — O(1).

Ловушки

  • У равных ключей обязан быть одинаковый хеш; обратное необязательно. Хеш-код не уникален и не криптографический.
  • Изменение полей ключа, участвующих в хешировании, после вставки ломает поиск. Предпочитай неизменяемые ключи.
  • Dictionary не поддерживает конкурентные записи. ConcurrentDictionary безопасен для своих операций, но делегаты GetOrAdd/AddOrUpdate могут вызываться более одного раза.
  • Перебор обычных коллекций при модификации часто приводит к InvalidOperationException. List<T> хранит непрерывный массив: удвоение ёмкости — копирование O(n).
УточнениеПочему в Dictionary бывает O(n)?+
При большом числе коллизий просмотр одной цепочки может пройти много записей. Хорошая функция хеширования и подходящий IEqualityComparer делают обычный доступ близким к O(1).
УточнениеКак HashSet связан с Dictionary?+
Обе структуры основаны на хешировании; HashSet хранит только уникальные значения, а Dictionary — пары ключ/значение.
УточнениеПочему LinkedList не всегда быстрее List при вставках?+
Поиск места в LinkedList O(n), узлы выделяются отдельно и хуже локальность кеша CPU. Если узел заранее известен, вставка O(1); реальные измерения важнее одной Big O.

Поиск: когда какой

Линейный поиск: просматриваем элементы по очереди, O(n), сортировка не нужна. Бинарный поиск: сравниваем с серединой и отбрасываем половину, O(log n), но требует упорядоченного массива или другой структуры с эффективным доступом к середине.

BFS и DFS — обход графа

Граф состоит из вершин и рёбер. Обычно храним его как список соседей. Для графа с циклами помечаем посещённые вершины, чтобы не ходить по кругу.

BFS: A → B → C → D → E → F → G (по уровням). DFS (один из порядков): A → B → D → E → C → F → G (в глубину).

Сортировки и точность — только основное

QuickSort в среднем O(n log n), в худшем O(n²); MergeSort O(n log n), но обычно нужна дополнительная память O(n). В реальном C# чаще используем Array.Sort/List.Sort, а на интервью объясняем идею и ограничения.

Численные расчёты: double хранит двоичное приближение дробей, поэтому сравнение результатов вычислений часто требует допуска; decimal удобен для денежных расчётов, но не «более точный во всех задачах». Для скользящего среднего поддерживай сумму окна, добавляя новый элемент и вычитая старый: O(n) для n отсчётов вместо пересчёта каждого окна с нуля.

УточнениеПочему BFS находит кратчайший путь, а DFS — не обязательно?+
BFS исследует вершины по возрастанию числа пройденных рёбер. Поэтому первое достижение вершины даёт кратчайший путь в невзвешенном графе. DFS может сначала зайти в длинную ветку.
УточнениеПочему два алгоритма с одинаковым Big O работают с разной скоростью?+
Big O не учитывает константы, локальность памяти, аллокации и входные данные. Для реальной оптимизации нужны измерения.

06. Потоки, ThreadPool и Task — что запускается и где

Главный принцип: Thread — физический поток выполнения; Task — обещание завершения операции и её результата. Task не равен одному потоку, а async/await сами по себе новый поток не создают.

Всегда ли Task исполняется в одном потоке?

Нет. Task.Run запускает синхронный делегат на worker-потоке ThreadPool. Если делегат содержит await, его продолжение после ожидания может выполниться на другом worker-потоке. При настоящем асинхронном I/O поток не обязан простаивать во время ожидания. В UI-приложении await по умолчанию захватывает контекст UI и часто возвращает продолжение на UI-поток.

new Task(...) + Start() существует, но для обычного кода предпочтительнее Task.Run. Task.Factory.StartNew даёт расширенные настройки планировщика, но с async-делегатом может дать вложенный Task<Task>; использовать осознанно.

Гонки и правила

counter++ — чтение, сложение и запись; два потока могут потерять обновление. Race condition — результат зависит от порядка исполнения. Для простого счётчика — Interlocked, для сложной общей структуры — lock или изоляция данных. Избегай блокирующих .Result/.Wait() и Thread.Sleep на UI-потоке.

УточнениеМожно ли вызвать Task.Run, но так и не создать новый поток?+
Task.Run ставит работу в ThreadPool; пул обычно переиспользует существующий поток, а не создаёт новый при каждом вызове.
УточнениеЧто выбрать для обработки тяжёлых вычислений из WinForms?+
await Task.Run(() => Compute()), если вычисление действительно CPU-bound; после await обновить UI на его контексте. Для HTTP/Socket/БД с async API — сразу await XxxAsync(), без лишнего Task.Run.
УточнениеЧем concurrency отличается от parallelism?+
Concurrency — задачи могут продвигаться независимо и чередоваться; parallelism — выполнение вычислений одновременно на разных ядрах.

07. Примитивы синхронизации: Monitor, Interlocked, volatile, семафоры

Monitor: зачем нужен объект?

Вызовы Monitor.Enter(gate) синхронизируются по идентичности конкретного ссылочного объекта. Это «ключ» блокировки: два разных объекта — две независимые блокировки, даже если содержимое одинаково. Обычно пишут private readonly object _gate = new();. Не используй this, интернированные строки или публичный объект — сторонний код сможет случайно заблокировать его. Boxing структуры создал бы новую оболочку, поэтому значимые типы нельзя использовать как корректный стабильный идентификатор Monitor.

lock(gate) для обычного объекта концептуально разворачивается в Monitor.Enter + try/finally + Monitor.Exit. Enter(gate, ref lockTaken) помогает корректно освободить монитор, если вход завершился исключением. TryEnter(gate, millisecondsTimeout) может вернуть false, если не удалось захватить за отведённое время. Monitor реентерабелен для того же потока.

C#
private readonly object _gate = new();
private int _count;

public bool TryAdd()
{
    bool taken = false;
    try
    {
        Monitor.TryEnter(_gate, TimeSpan.FromMilliseconds(100), ref taken);
        if (!taken) return false;
        _count++;
        return true;
    }
    finally
    {
        if (taken) Monitor.Exit(_gate);
    }
}

Monitor.Wait, Pulse, PulseAll — ожидание условия

Wait(gate) вызывается внутри захваченного Monitor, временно освобождает его и ждёт сигнала, затем вновь захватывает перед возвратом. Pulse уведомляет одного ожидающего, PulseAll — всех. Уведомление не означает, что условие уже истинно или поток немедленно получит lock. Поэтому условие проверяют через while, а не if.

C#
lock (_gate)
{
    while (_queue.Count == 0)
        Monitor.Wait(_gate); // отпускает lock, ждёт, затем захватывает
    item = _queue.Dequeue();
}
// Producer: lock (_gate) { _queue.Enqueue(x); Monitor.Pulse(_gate); }

volatile vs Interlocked — разница по шагам

volatile (или Volatile.Read/Write) накладывает гарантии видимости и порядка определённых чтений/записей между потоками. Но x++ всё равно состоит из нескольких шагов: прочитал → увеличил → записал. Два потока могут прочитать одно старое значение и записать одинаковое новое. Для атомарного инкремента используй Interlocked.Increment(ref x).

Interlocked выполняет операции как одно неделимое изменение: Increment, Decrement, Add, Exchange (безусловная замена), CompareExchange (заменить, только если текущее значение совпадает с ожидаемым). У операций также есть необходимые гарантии упорядочивания памяти. Для согласованного изменения нескольких независимых полей обычно нужен lock или другой протокол синхронизации.

C#
private int _counter;
private int _state;

Interlocked.Increment(ref _counter);
int oldValue = Interlocked.Exchange(ref _state, 42);

// CAS: поставить 1 только если состояние ещё 0:
int previous = Interlocked.CompareExchange(ref _state, 1, 0);
bool success = previous == 0;

// CAS-цикл: обновление из текущего значения (могут быть повторы):
int before, after;
do
{
    before = Volatile.Read(ref _counter);
    after = before + 10;
}
while (Interlocked.CompareExchange(ref _counter, after, before) != before);
CAS (Compare-And-Swap): условная атомарная замена
Читаем old→Считаем new→CompareExchange(old → new)→Не совпало? Повторяем

CAS позволяет избежать традиционного захвата lock для отдельных обновлений; при высокой конкуренции поток может многократно повторять попытку.

Semaphore / SemaphoreSlim: счётчик и очередь ожидания

Допустим, new SemaphoreSlim(2, 2): начальное число разрешений = 2, максимум = 2. Два потока входят после Wait/WaitAsync; третий ожидает. Когда первый завершит работу и вызовет Release(), один ожидающий сможет получить разрешение. Очередь ожидания существует логически, но FIFO не гарантируется: порядок пробуждения не равен строгому порядку поступления запросов.

SemaphoreSlim(2, 2)
Разрешение #1: A работаетРазрешение #2: B работает│C / D ждут→ Release()Один ожидающий войдёт

Семафор ограничивает количество параллельных операций, но не защищает произвольные данные сам по себе и не обещает справедливую FIFO-очередь.

C#
using var slots = new SemaphoreSlim(initialCount: 2, maxCount: 2);

await slots.WaitAsync(cancellationToken);
try
{
    await SendRequestAsync(cancellationToken);
}
finally
{
    slots.Release(); // иначе разрешение будет потеряно
}

Параметры и ловушки: у WaitAsync(timeout, ct) перегрузка с таймаутом возвращает bool; отмена — исключение OperationCanceledException. Release() сверх maxCount вызывает SemaphoreFullException. Mutex.WaitOne(timeout) и ReleaseMutex() ориентированы на владение потоком; SemaphoreSlim не отслеживает владельца разрешения. await нельзя помещать внутрь обычного lock; для async-критической секции подходит SemaphoreSlim(1,1).

УточнениеПочему Monitor.Enter(new object()) ничего не защищает?+
Каждый вызов получает новый объект блокировки. Другие потоки используют другие идентификаторы и не конкурируют за один monitor.
УточнениеПочему volatile counter++ не потокобезопасен?+
volatile регулирует чтение и запись, но не объединяет три операции (чтение, сложение, запись) в одну атомарную. Нужен Interlocked.Increment.
УточнениеГарантирует ли SemaphoreSlim FIFO?+
Нет. Даже если несколько потоков ожидают разрешения, порядок получения не гарантирован.
УточнениеВ чём разница между Wait и Pulse у Monitor?+
Wait отпускает monitor и ждёт; Pulse подаёт сигнал одному ожидающему, не отдавая ему lock немедленно. Ожидающий продолжит после повторного захвата.

08. async/await и Task

Асинхронность — не синоним многопоточности.

P0

Что делает компилятор

async разрешает await; компилятор создаёт state machine. Метод исполняется синхронно до первого незавершённого await; затем возвращает Task, а продолжение запускается после завершения операции. await сам по себе не запускает новый поток.

Call async→Run sync→await I/O→return control→continuation
СценарийХороший выборПочему
HTTP/DB/socket запросawait SomeAsync()не держим поток на время I/O

SynchronizationContext: почему WinForms может зависнуть

WinForms использует контекст синхронизации, который направляет продолжение await обратно в UI-поток (по умолчанию, когда контекст захвачен). Если UI-поток делает .Result, он блокирует себя и не даёт продолжению завершиться — deadlock. Правило: async all the way.

C#
// ПЛОХО: потенциальный deadlock на UI
private void button1_Click(object sender, EventArgs e)
    => label1.Text = LoadTextAsync().Result;

// ХОРОШО: обработчик событий может быть async void
private async void button1_Click(object sender, EventArgs e)
{
    button1.Enabled = false;
    try { label1.Text = await LoadTextAsync(); }
    catch (Exception ex) { MessageBox.Show(ex.Message); }
    finally { button1.Enabled = true; }
}

ConfigureAwait, отмена, исключения

  • ConfigureAwait(false) говорит не пытаться возобновлять на захваченном контексте; полезно в библиотечном коде, когда UI не требуется. Это не гарантирует отдельный поток и не лечит архитектуру «блокируем Result».
  • CancellationToken — кооперативная отмена. Передавай токен вниз, проверяй его при длительных CPU-циклах, обрабатывай OperationCanceledException отдельно от ошибок.
  • Task.WhenAll завершится после всех задач, при ошибке Task содержит сведения обо всех исключениях; await обычно выбрасывает одно. Для всех смотри Task.Exception.
  • async void допускается для UI event handler, но плохо для обычных методов — вызывающий код не может await и ловить исключения обычным способом.
  • ValueTask<T> полезен на горячем пути при частом синхронном завершении, но имеет ограничения потребления; используй после профилирования.
C#
// Параллельные запросы: задачи создаются до WhenAll
Task<string> a = http.GetStringAsync(urlA, ct);
Task<string> b = http.GetStringAsync(urlB, ct);
string[] result = await Task.WhenAll(a, b);

// Реальная отмена:
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(5));
string response = await http.GetStringAsync(urlA, timeout.Token);
УточнениеМожет ли async-метод завершиться синхронно?+
Да: до первого незавершённого await метод выполняется на вызывающем потоке; если все ожидаемые задачи уже завершены, может завершиться целиком синхронно.
УточнениеTask.WhenAll создаёт потоки?+
Нет. Он агрегирует завершение уже запущенных операций. Для IO задачи могут не требовать потока ожидания; для CPU используем Task.Run/Parallel по ситуации.
УточнениеМожно ли делать Task.Run для HTTP-запроса?+
Обычно бессмысленно: HttpClient уже поддерживает неблокирующий I/O. Task.Run добавит планирование и расход ресурсов. Важно корректно awaited операцию.
УточнениеПочему SemaphoreSlim предпочтительнее lock в async?+
У SemaphoreSlim есть WaitAsync, позволяющий не блокировать поток на время ожидания, а lock нельзя держать через await. Для доступа по одному используй SemaphoreSlim(1, 1).

09. Потоковая обработка и визуализация данных

Поток измерений → обработка → ограниченная память → стабильные графики.

P0

Сквозной конвейер данных

Socket / File→Parser→Bounded Channel→Processing→Snapshots / UI
  • Не обновлять график на каждый пакет: 10 000 измерений/с ≠ 10 000 перерисовок/с. UI должен получать snapshots, например 10–30 раз/с в зависимости от задачи.
  • Backpressure: ограниченная ёмкость буфера; политика при перегрузке выбирается по потере данных: ждать, записывать на диск, отбрасывать устаревшие кадры отображения (не сырые измерения).
  • Кольцевой буфер: O(1) запись и фиксированная память; полезен для последних N отсчётов.
  • Downsampling: простой выбор каждого N-го может пропустить короткий пик. Min/max bucket сохраняет локальные экстремумы; LTTB применяют для репрезентативных графиков, если метод подходит данным.
  • Разделять частоты: ingestion, вычисления и rendering имеют разные SLA. Рендер не должен блокировать приём/сохранение данных.
C#
// .NET 6+: граница между producer и consumer
var channel = Channel.CreateBounded<Measurement>(new BoundedChannelOptions(1024)
{
    FullMode = BoundedChannelFullMode.Wait,
    SingleReader = true,
    SingleWriter = false
});

// Producer (сеть):
await channel.Writer.WriteAsync(item, ct);
// Consumer (обработчик):
await foreach (var m in channel.Reader.ReadAllAsync(ct))
    Process(m); // CPU-bound: учитываем скорость consumer

// Channel<T> подключается через using System.Threading.Channels;

Разделение ответственности и измерения

Выделить IDataSource, IProtocolParser, IProcessingStage, IChartModel; вход и выход каждого этапа — понятные DTO. В метриках: размер очереди, dropped frames, задержка от приёма до визуализации, скорость обработки (samples/sec), аллокации/с.

УточнениеПочему график тормозит, хотя CPU загружен на 15%?+
Может быть перегружен единственный UI thread тысячами update/аллоцирования; проверить очередь сообщений, профилировщик UI, число элементов на графике, частоту redraw.
УточнениеКак сохранить пики при сокращении миллиона точек до тысячи?+
Вместо прореживания каждого N-го взять min и max каждого окна (порядок точек сохранить); так экстремумы не пропадут. Это не универсальная замена агрегатам анализа, исходные данные хранить отдельно.
УточнениеЧто если consumer медленнее producer на протяжении часа?+
Без bounded buffer память будет расти. Вводим backpressure / spool на диск, ограничение скорости, масштабирование или чёткую политику потерь; мониторим latency и длину очереди.

Как работает Protobuf

В .proto у поля есть стабильный номер, имя и тип. Кодогенератор создаёт типы клиента/сервера; wire format использует номер поля + wire type, varint для ряда чисел, length-delimited для строк/сообщений. Не переиспользовать номера удалённых полей; использовать reserved. Новые поля должны быть необязательными для старого клиента по смыслу; важны правила proto3 default и изменения типов.

proto
syntax = "proto3";
package telemetry;
message Measurement {
  int64 timestamp_unix_ms = 1;
  double value = 2;
  string sensor_id = 3;
  reserved 4; // номер больше не использовать
}

  • JSON: System.Text.Json поддерживает настройку именования, converters, source generation; незнакомые поля, case-sensitivity и nullable/default необходимо проверять настройками и тестами.
  • XML: XmlReader — потоковый; XmlSerializer сопоставляет объекты. На непроверенном вводе избегать включения разрешения внешних сущностей (XXE), устанавливать безопасные параметры чтения.

УточнениеПочему Protobuf часто меньше JSON?+
Передаёт бинарные значения и идентификаторы полей, а не повторяющиеся текстовые имена полей; varint экономит место на небольших целых. Размер зависит от данных и схемы.
УточнениеМожно ли переименовать поле в .proto без поломки?+
Для бинарного Protobuf важнее сохранение номера и wire-совместимого типа. При JSON-mapping Protobuf и внешних клиентах имя поля может иметь значение; менять осторожно.
УточнениеЧто делать с неизвестным типом/полем JSON?+
Определить контракт: игнорировать или отвергать, явно управлять настройками десериализации, валидировать обязательные данные, диапазоны и размер. Игнорировать неизвестное поле без проверки бизнес-инвариантов опасно.
УточнениеПочему нельзя сразу передавать объект из JsonSerializer.Deserialize в алгоритм?+
Десериализация подтверждает формат, но не корректность по бизнес-правилам: обязательность, диапазоны, единицы, временные метки, максимальные размеры. Нужна отдельная валидация.

Framing в TCP — как отделить сообщения

TCP отдаёт поток байтов: один Send не равен одному Read. Способы выделять сообщения: фиксированная длина; разделитель (например, \n, с экранированием при необходимости); или length-prefix — сначала размер полезной нагрузки, затем ровно столько байтов.

C#
// Пример: сообщение «длина (4 байта, big endian) + тело»
byte[] header = new byte[4];
await stream.ReadExactlyAsync(header, cancellationToken);
int length = System.Buffers.Binary.BinaryPrimitives.ReadInt32BigEndian(header);
if (length < 0 || length > 1024 * 1024) throw new InvalidDataException();
byte[] payload = new byte[length];
await stream.ReadExactlyAsync(payload, cancellationToken);
// ReadExactlyAsync доступен в современном .NET; для старых версий нужен цикл чтения.
УточнениеTCP гарантирует доставку одного сообщения целиком за один Receive?+
Нет. TCP гарантирует порядок байтов, а не границы сообщений. Нужно собрать сообщение из нескольких чтений согласно своему протоколу framing.
УточнениеЧто надёжнее: UDP или HTTP?+
Это разные уровни. UDP сам по себе не гарантирует доставку; HTTP/1.1 и HTTP/2 обычно используют TCP, HTTP/3 — QUIC поверх UDP с собственной надёжной доставкой.
УточнениеПочему WebSocket может быть удобнее частого HTTP polling?+
Держит логическое двустороннее соединение, сервер отправляет данные без постоянных новых запросов. Нужно продумать reconnect, heartbeat и обработку разрывов.

14. SQL: язык запросов, оконные функции и индексы

От SELECT и JOIN до B-tree, EXPLAIN и транзакций — понятными примерами.

P0
SQL (Structured Query Language) — декларативный язык: ты описываешь какие данные нужны, а СУБД выбирает как их получить. Важные части: фильтрация, соединения, группировка, оконные функции, индексы и план выполнения.

Логический порядок обработки: FROM/JOIN → WHERE → GROUP BY → HAVING → оконные функции → SELECT → ORDER BY → LIMIT (упрощённо; оптимизатор вправе выбрать другой физический план, сохраняя смысл). WHERE не фильтрует результат агрегата; для этого нужен HAVING.

SQL
SELECT department_id, COUNT(*) AS people, AVG(salary) AS avg_salary
FROM employees
WHERE active = true
GROUP BY department_id
HAVING COUNT(*) >= 2
ORDER BY avg_salary DESC;

JOIN, CTE и подзапросы

INNER JOIN — только совпавшие строки; LEFT JOIN — все строки слева, справа NULL без совпадения; RIGHT/FULL JOIN — аналогично справа / с обеих сторон (поддержка зависит от СУБД). Условие в WHERE по правой таблице после LEFT JOIN может незаметно отфильтровать строки без совпадений. CTE через WITH — именованный результат внутри одного SQL-оператора, улучшает читаемость; сам по себе не гарантирует ни кеширования, ни ускорения.

SQL
WITH active_depts AS (
    SELECT department_id, COUNT(*) AS cnt
    FROM employees WHERE active = true
    GROUP BY department_id
)
SELECT d.name, a.cnt
FROM departments d
LEFT JOIN active_depts a ON a.department_id = d.id;

Оконные функции — на конкретном примере

Главное отличие от GROUP BY: GROUP BY сворачивает много строк в одну на группу; оконная функция вычисляет показатель по группе строк, сохраняя каждую исходную строку. В OVER(PARTITION BY department_id ORDER BY salary DESC) PARTITION BY делит на группы, ORDER BY задаёт порядок внутри каждой группы.

SQL
SELECT name, department_id, salary,
       ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS pos,
       AVG(salary) OVER (PARTITION BY department_id) AS department_avg,
       LAG(salary) OVER (PARTITION BY department_id ORDER BY salary DESC) AS previous_salary
FROM employees;

Индекс с нуля: что хранится и почему помогает

Представь телефонный справочник, отсортированный по фамилии. Вместо просмотра каждой записи СУБД идёт по узлам сбалансированного B-tree/B+tree: от корня выбирает диапазон ключей, спускается к листьям и находит нужные записи. Во многих СУБД используют варианты B-tree; устройство листьев и связь с таблицей зависит от движка.

Транзакции — что помнить

ACID: атомарность (всё или ничего), согласованность, изоляция, долговечность. Транзакции нужны, когда несколько изменений должны составить одну операцию. Lost update — один конкурентный апдейт перезаписал другой; dirty read — чтение неподтверждённых данных; phantom read — повторный запрос видит другой набор строк. Уровни изоляции и работа блокировок/MVCC зависят от СУБД.

УточнениеОконная SUM() OVER(...) уменьшает число строк?+
Нет, оконная функция вычисляет значение для каждой строки без свёртки всей группы. Сворачивает строки GROUP BY.
УточнениеПочему индекс (A, B) не всегда помогает при WHERE B = ...?+
В обычном B-tree отсортировка начинается с A. Без ограничения по ведущему столбцу оптимизатор может предпочесть сканирование или особые возможности движка.
УточнениеПочему Index Scan не всегда плохо?+
Когда нужно прочитать большую часть строк, последовательный проход часто дешевле большого числа случайных обращений. Всегда смотри реальный план и объём данных.

if (user is not null) { user.Name = "New"; await db.SaveChangesAsync(); }

Change Tracking и состояния

DbContext запоминает загруженные отслеживаемые сущности и обнаруживает изменения. Состояния Added, Modified, Deleted, Unchanged, Detached определяют, какую SQL-команду нужно сформировать. Вызов SaveChanges отправляет изменения; обычное присваивание свойства без сохранения не обновляет БД.

N+1 и загрузка связанных объектов

N+1: получили список из N пользователей, затем по одному дополнительному запросу получили заказы каждого. Решения: Include для eager loading, Select с нужной проекцией, либо продуманная split query. Lazy loading может скрывать обращения к БД за доступом к свойству; явная загрузка выполняется отдельным запросом по команде разработчика.

C#
// Обычно лучше выбирать нужные данные, а не грузить все сущности:
var summary = await db.Users
    .Select(u => new { u.Name, OrdersCount = u.Orders.Count })
    .ToListAsync();

// Для просмотра SQL (без выполнения):
string sql = db.Users.Where(u => u.IsActive).ToQueryString();

Миграции, транзакции, конкурентность

Migrations хранят версии структуры БД и применяют их через CLI/CI. Один SaveChanges для поддерживающего транзакции провайдера по умолчанию выполняется атомарно, когда это применимо. Для проверки, что конкурентный пользователь не перезаписал изменения, используют optimistic concurrency и concurrency token (например, rowversion в SQL Server), обрабатывая DbUpdateConcurrencyException.

Время жизни: DbContext не потокобезопасен. Не запускай на одном контексте два запроса параллельно, не делай его singleton. В веб-приложениях типичен scoped-контекст на запрос, в desktop — короткоживущий контекст на операцию/единицу работы, при необходимости через IDbContextFactory. Параметризированные LINQ-запросы снижают риск SQL injection; с сырым SQL нельзя вставлять непроверенные пользовательские строки.

УточнениеВ чём разница IQueryable и IEnumerable?+
IQueryable позволяет провайдеру перевести выражение в SQL; после материализации (ToList) следующие операции могут выполняться в памяти. Не каждое C#-выражение переводится в SQL.
УточнениеМожно ли использовать один DbContext в Task.WhenAll?+
Нет. Один DbContext не предназначен для параллельных операций. Для независимых одновременных запросов — отдельные экземпляры.
УточнениеЧто произойдёт при AsNoTracking и изменении свойства результата?+
EF обычно не отслеживает этот объект, поэтому изменение свойства само по себе не будет сохранено через текущий контекст. Нужно явно присоединить/обновить сущность либо загрузить её с tracking.

16. ООП, виды полиморфизма, SOLID и IoC

Overload/override/new, DI-контейнер и время жизни зависимостей.

P0
ООП: инкапсуляция скрывает детали; наследование расширяет поведение; абстракция выделяет важное; полиморфизм позволяет работать через общий контракт с разными реализациями. Предпочитай композицию, когда не требуется отношение «является».

{
    public virtual string Speak() => "...";
}

{

IoC, DI и DIP — не одно и то же

IoC (Inversion of Control) — инверсия управления: создание, связывание и запуск компонентов передаются внешнему механизму вместо жёсткого управления изнутри объекта. DI (Dependency Injection) — один из способов реализовать IoC: зависимости передаются в конструктор/метод/свойство. DIP — принцип SOLID: высокоуровневая логика опирается на абстракции, а не напрямую на конкретную БД/сеть.

C#

Composition Root — точка настройки зависимостей при запуске приложения. Контейнер Microsoft.Extensions.DependencyInjection создаёт объекты и управляет временем жизни: Transient — новый экземпляр при разрешении; Scoped — один на область (например, HTTP-запрос или явно созданный scope в desktop); Singleton — один на контейнер. Singleton, удерживающий scoped-сервис, — ошибка жизненного цикла. Service Locator скрывает зависимости за вызовами контейнера внутри бизнес-кода; внедрение через конструктор делает контракт явным.

УточнениеDI и IoC — синонимы?+
Нет. IoC — широкий принцип передачи управления; DI — один способ его реализовать; DIP — принцип зависимости от абстракций.
УточнениеПочему new и override дают разный результат при вызове через Animal?+
override участвует в виртуальной диспетчеризации по фактическому типу объекта. new лишь скрывает имя метода в наследнике, выбор зависит от типа переменной.
УточнениеЧто делает Scoped в WinForms?+
Сам по себе ничего «на форму» не привязывает. Нужно явно определить жизненный цикл и создавать/освобождать IServiceScope, например на окно или операцию.

УточнениеStrategy и State — в чём разница?+
Структурно оба делегируют поведение объекту. Strategy — внешний выбор взаимозаменяемого алгоритма; State — переходы жизненного цикла, где сам объект меняет поведение по текущему состоянию.
УточнениеAdapter vs Decorator vs Facade?+
Adapter меняет интерфейс, Decorator сохраняет интерфейс и добавляет поведение, Facade представляет простой вход в сложную подсистему.
УточнениеКогда Singleton — ошибка?+
Когда единичность не является бизнес-инвариантом, а глобальная мутабельность затрудняет тестирование, параллелизм и время жизни. Регистрация singleton в DI не делает внутренний объект потокобезопасным.
УточнениеFactory Method vs Abstract Factory?+

УточнениеЗачем Circuit Breaker, если есть Retry?+
Retry повторяет отдельную ошибку; Circuit Breaker открывает цепь при систематических ошибках, чтобы не перегружать недоступную зависимость. Обычно используют вместе, с лимитами и метриками.

18. Исключения: throw, Task и многопоточность

Где возникает и где обрабатывается ошибка, AggregateException и отмена.

P0
Главное: исключение не перепрыгивает автоматически между потоками. В Task оно записывается в состояние задачи и при await выбрасывается снова в коде ожидания. Поэтому место создания задачи и место обработки ошибок могут различаться.
ЗаписьЧто означает
throw new Exception(...)Создать и бросить новое исключение
throw;Повторно бросить текущее из catch с сохранением исходной трассы
throw ex;Сбрасывает/изменяет участок исходной stack trace — обычно избегать
catch (X ex) when (...)Обработать исключение только при условии фильтра
finallyОсвободить ресурс / восстановить состояние даже при исключении
C#
try { DoWork(); }
catch (IOException ex) when (ex.HResult != 0)
{
    Log(ex);
    throw; // сохраняем исходное место ошибки
}
finally { Cleanup(); }

Разные потоки: что поймает try/catch

Код try { new Thread(Action).Start(); } перехватывает ошибку запуска потока, но не исключение, которое позже произойдёт внутри Action на другом потоке. Необработанное исключение на обычном Thread/ThreadPool в современном .NET обычно завершает процесс. Нужно ловить ошибку внутри потока или передавать результат/ошибку вызывающему коду через Task/Channel/другой механизм.

C#
// НЕ перехватит ошибку внутри Thread:
try { new Thread(() => throw new InvalidOperationException()).Start(); }
catch (InvalidOperationException) { /* сюда не попадём */ }

// Task хранит ошибку; await её повторно выбросит:
try
{
    await Task.Run(() => throw new InvalidOperationException("fail"));
}
catch (InvalidOperationException ex) { Log(ex); }

await, Wait, Result и несколько ошибок

Если Task завершилась с ошибкой, await выбрасывает исходное исключение (при нескольких ошибках обычно одно из них), Wait()/.Result при ошибке обычно бросают AggregateException. Для Task.WhenAll Task.Exception содержит агрегированные ошибки от всех упавших задач; если надо обработать каждую, проанализируй Exception.InnerExceptions завершённой общей задачи. async void не даёт Task вызывающему коду, ошибки уходят в контекст синхронизации / обработчик необработанных исключений — допустим в первую очередь в UI-event handlers.

C#
var all = Task.WhenAll(DoAAsync(), DoBAsync());
try { await all; }
catch
{
    if (all.Exception is { } aggregate)
        foreach (var error in aggregate.InnerExceptions)
            Log(error);
}

Fire-and-forget: просто вызвать Task и забыть — значит потерять контроль над отменой и ошибками. Предпочтительнее хранить Task/await или запускать контролируемый фоновый сервис с логированием. ExceptionDispatchInfo.Capture(ex).Throw() позволяет перебросить исключение за границей другого вызова, сохраняя исходную трассу.

Отмена — это не обычная ошибка

CancellationToken передаёт запрос на отмену. Код проверки вызывает ThrowIfCancellationRequested(), выбрасывая OperationCanceledException; TaskCanceledException наследуется от неё. Когда Task правильно связывает отмену со своим токеном, она переходит в статус Canceled, а не Faulted. Проверяй, что именно отменило операцию, и не проглатывай все исключения общим catch (Exception).

УточнениеПерехватит ли try/catch исключение Task.Run без await?+
Не автоматически. Исключение сохранится в Task; его нужно наблюдать через await, Wait или Exception завершённой задачи.
УточнениеПочему .Result опасен в WinForms?+
Блокирует UI-поток, а продолжение async-операции может ожидать этот же UI SynchronizationContext → взаимная блокировка (deadlock).
УточнениеПочему await Task.WhenAll не обязательно выбрасывает AggregateException?+
await распаковывает и обычно выбрасывает одно исключение, хотя WhenAll-Task хранит набор ошибок в Exception.InnerExceptions.

Mock — проверяем взаимодействия; Stub — предсказуемый ответ; Fake — упрощённая работающая реализация. Не нужно мокать каждый DTO. Unit-тесты проверяют контракт, а интеграционные — реальные границы (SQL, sockets, сериализацию).

Что обязательно тестировать в этой вакансии

  • TCP: пакет разбит на 1–N чтений; два пакета пришли вместе; длина недопустима; peer отключился на середине.
  • Async: таймаут, CancellationToken, повтор подключения, обработка exception, отсутствие зависания UI.
  • БД: транзакция rollback, конфликт параллельных обновлений, constraints, корректные параметры.
  • Thread safety: барьеры для контролируемой гонки, инварианты, многократные стресс-прогоны; тесты на таймингах могут быть flaky.
  • Regression: каждая исправленная ошибка должна по возможности стать тестом.
C#
[Test]
public async Task Cancelled_request_throws()
{
    using var cts = new CancellationTokenSource();
    cts.Cancel();
    Assert.ThrowsAsync<OperationCanceledException>(async () =>
        await Task.Delay(1000, cts.Token));
}
// NUnit, показан минимальный вариант
