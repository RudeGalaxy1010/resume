01

C# Core

Типы, передача данных, ООП, коллекции и делегаты.

Value type хранит значение целиком; reference type — ссылку на объект. Это не равно «stack против heap»: место хранения зависит от контекста. При присваивании struct копируется значение, при присваивании class — ссылка.

Value type и reference type

Value typeReference type
Примерыint, bool, enum, structclass, array, delegate, string
Переменная содержитСамо значениеСсылку на объект
ПрисваиваниеКопирует значениеКопирует ссылку
DefaultНулевое значение полейnull
НаследованиеНет наследования от другого structКлассы поддерживают наследование
struct Position { public int X; }
class Player { public int Hp; }

var p1 = new Position { X = 1 };
var p2 = p1;       // полная копия Position
p2.X = 9;          // p1.X всё ещё 1

var a = new Player { Hp = 100 };
var b = a;         // две ссылки на один Player
b.Hp = 10;         // a.Hp тоже 10
Фраза «struct находится на стеке, class — в куче» неверна. Struct может быть полем объекта в managed heap, элементом массива или частью замыкания. Stack/heap — детали размещения, value/reference — семантика значения.

Передача параметров

По значению — default

Метод получает копию переменной. Для class копируется ссылка, поэтому состояние объекта менять можно, а переназначение локальной ссылки снаружи не видно.

ref

Чтение и запись исходной переменной. Она обязана быть инициализирована до вызова.

out

Метод обязан присвоить значение. Входное значение читать до присваивания нельзя.

in

Readonly-ссылка. Полезна для больших struct, но не гарантирует ускорение: маленькие структуры проще копировать.

Запоминалка: ref — read/write, out — output, in — input readonly.

Boxing и unboxing

Value type→ boxing →Объект в managed heap→ unboxing →Проверка типа + копия значения

Boxing возникает при преобразовании value type в object или интерфейс. CLR создаёт объект в managed heap и копирует значение. Это allocation. Unboxing требует совместимого точного типа.

int value = 42;
object boxed = value;       // boxing + allocation
int copy = (int)boxed;    // unboxing

void Log(object x) { }
Log(value);                  // boxing

Class, struct, record

  • Class — идентичность, совместно используемое изменяемое состояние, полиморфизм.
  • Struct — небольшое значение без собственной идентичности: координата, цвет, диапазон. Предпочтительно immutable/readonly.
  • Record — удобная семантика данных: value-based equality, with, init-only. Record может быть class или struct.
  • ref struct — stack-only ограничение для безопасной работы с памятью, например Span<T>. Нельзя обычным образом хранить в heap или боксить.

Полиморфизм: virtual, override и new

class Base { public virtual void Run() => Print("Base"); }
class Child : Base {
  public override void Run() => Print("Override");
}

Base x = new Child();
x.Run(); // Override: виртуальный dispatch по runtime-типу

new не переопределяет, а скрывает член. Выбор зависит от compile-time типа ссылки. На интервью обычно важно сказать: override поддерживает полиморфизм, new легко создаёт неожиданное поведение.

Covariance и contravariance

Covariance — наружу: IEnumerable<Cat> можно использовать как IEnumerable<Animal>, потому что источник только отдаёт значения. Contravariance — внутрь: обработчик любого Animal подходит там, где нужен обработчик Cat.

Запоминалка: out — производитель, in — потребитель. Если API и отдаёт, и принимает T, вариантность обычно невозможна.

Delegates, events и closures

Delegate — типобезопасная ссылка на один или несколько методов. event ограничивает внешний код: подписчики могут только +=/-=, а вызвать событие способен владелец.

for (int i = 0; i < enemies.Count; i++)
{
    int index = i;
    buttons[i].Clicked += () => Select(enemies[index]);
}

Lambda становится closure, если захватывает внешнее состояние. Компилятор обычно создаёт скрытый объект-контейнер. Опасности: allocation, непреднамеренное удержание объектов, неправильная отписка при новой lambda.

«Почему композиция лучше наследования?»
Композиция позволяет независимо менять поведение, уменьшает связанность и избегает хрупкой глубокой иерархии. Наследование оставляю для настоящего отношения is-a и стабильного общего контракта; игровые способности чаще моделирую отдельными компонентами/стратегиями.
02

C# Advanced, память и async

Managed heap, GC, allocations, generics и state machines.

GC освобождает недостижимые managed-объекты, но не управляет lifetime нативных ресурсов Unity. Главная цель в realtime-коде — не «ноль аллокаций везде», а отсутствие непредсказуемых spikes в чувствительных циклах.

Модель managed-памяти

GC roots
static / stack / handles→Достижимые объекты✓Остаются
Недостижимые→GC collection→Память пригодна для reuse

Сборщик начинает от корней и отмечает граф достижимых объектов. То, до чего добраться нельзя, считается мусором. Unity использует Boehm GC: в актуальной документации он описан как non-generational и non-compacting. Поэтому привычное объяснение про Gen 0/1/2 из современного .NET нельзя механически переносить на Unity runtime.

«GC поколений Unity» — частая ошибка ответа. Уточняй runtime и backend. В Unity ключевыe понятия: managed heap, roots, incremental marking, non-compacting heap, allocations per frame.

Incremental GC

Вместо одной длинной stop-the-world паузы Unity делит marking на части по нескольким кадрам. Это снижает пик, но не делает работу бесплатной. Изменение ссылок требует write barriers, а высокая скорость новых allocations может не дать сборщику завершиться в бюджете.

Incremental GC меняет форму паузы, а не отменяет цену. Сначала убираем постоянный мусор, потом подбираем режим.

// Hot path: фильтруем без временного списка.
_aliveBuffer.Clear();
for (int i = 0; i < _enemies.Count; i++)
    if (_enemies[i].IsAlive)
        _aliveBuffer.Add(_enemies[i]);
LINQ не «плохой». Он уместен в Editor tooling, startup, редких операциях и там, где читаемость важнее микростоимости. Решение принимается по частоте, объёму и профилю build, а не по догме.

Managed и native memory

Texture2D, Mesh, AudioClip и другие UnityEngine.Object имеют managed wrapper и native payload. Потеря managed-ссылки не означает мгновенного освобождения native memory. Для созданных ресурсов нужны корректные Destroy, Release, unload и ownership.

Generics

  • where T : class — reference type.
  • where T : struct — non-nullable value type.
  • where T : unmanaged — тип без managed references, полезен для низкоуровневой памяти.
  • where T : new() — публичный parameterless constructor.

Generics дают compile-time type safety и часто избегают boxing, потому что код работает с конкретным T, а не object. Но конкретная генерация/разделение кода зависит от runtime и IL2CPP.

Как работает async/await

Вызов async→Выполнение до незавершённого await→Сохранение state→Continuation

Компилятор превращает метод в state machine. await не означает «создать поток»: он приостанавливает метод, если операция не завершена, и регистрирует продолжение. I/O может вообще не занимать поток во время ожидания; CPU-bound работу надо явно переносить или распараллеливать.

Исключения и отмена

  • В Task/UniTask исключение хранится в операции и выбрасывается при await.
  • async void нельзя нормально await; исключения уходят в context. Допустим прежде всего для event handlers.
  • CancellationToken — кооперативный сигнал. Метод должен его проверять или передавать вниз.
  • Timeout — частный случай отмены; полезно отличать пользовательскую отмену от таймаута.

Race condition и deadlock

Race возникает, когда результат зависит от порядка конкурентных действий. Даже в одном Unity thread возможна логическая гонка между interleaved continuations.

int version = ++_requestVersion;
var texture = await LoadAsync(key, token);

if (version != _requestVersion) {
    Release(texture);        // пришёл устаревший результат
    return;
}
Show(texture);

Deadlock классически появляется, когда thread блокируется через .Result/.Wait(), а continuation ждёт этот же context. В Unity также опасно смешивать блокирующее ожидание и main-thread-only API.

«Task, Coroutine или UniTask?»
Coroutine удобна для frame-based последовательностей, но слабо композируется и не возвращает типизированный результат. Task — стандарт .NET и хорош для I/O/библиотек, но может иметь лишнюю стоимость и не связан с PlayerLoop. UniTask адаптирован к Unity PlayerLoop и снижает allocations; в любом async-варианте явно проектирую отмену, lifetime и обработку исключений.
03

Unity Core

PlayerLoop, lifecycle, время, fake null и serialization.

Unity не вызывает «магические методы» как обычную цепочку на каждом объекте. Движок выполняет фазы PlayerLoop, внутри которых запускаются callbacks. Порядок разных объектов без явной настройки не стоит считать гарантированным.

PlayerLoop и lifecycle

Initialization→EarlyUpdate→FixedUpdate*→Update→Late / Render

FixedUpdate может выполниться 0, 1 или несколько раз перед визуальным кадром: Unity догоняет фиксированный timestep физики.

OnEnableПодписки, запуск активностиВызывается многократно
StartИнициализация перед первым UpdateТолько при enabled component
FixedUpdateШаги физикиНе «один раз на кадр»

Awake — «я существую», OnEnable — «я активен», Start — «первый запуск», OnDisable — «я неактивен», OnDestroy — «меня больше не будет».

Как гарантировать порядок

  1. Лучше убрать скрытую зависимость: явный composition root вызывает Initialize().
  2. Для инфраструктуры — DI container/lifecycle interfaces.
  3. Если callbacks неизбежны — Script Execution Order или DefaultExecutionOrder, но локально и осознанно.
  4. Не строить приложение на случайном порядке объектов сцены.

Time

deltaTime

Время между визуальными кадрами с учётом timeScale. Для frame-based движения.

fixedDeltaTime

Размер фиксированного физического шага, не фактическая длина render frame.

unscaledDeltaTime

Не зависит от timeScale. UI, pause-menu, независимые таймеры.

timeScale

Масштабирует игровое время; не является универсальной «паузой» для всех систем.

// frame-rate independent
transform.position += velocity * Time.deltaTime;

// физическое действие — обычно FixedUpdate
rb.AddForce(force, ForceMode.Force);

Unity fake null

UnityEngine.Object перегружает оператор равенства. После Destroy native object уничтожен, но managed wrapper может ещё существовать. Поэтому obj == null может быть true, хотя ReferenceEquals(obj, null) — false.

Null-conditional ?. и null-coalescing ?? основаны на CLR null, а не обязательно на Unity overloaded equality. Для уничтожаемых Unity Objects не смешивай проверки без понимания семантики.

Serialization

Unity сериализует поля, а не свойства; набор поддерживаемых типов ограничен правилами сериализатора. [SerializeField] показывает private field. [SerializeReference] нужен для managed references и полиморфных графов, но добавляет сложность формата и миграций.

Domain Reload

При входе в Play Mode domain reload обычно пересоздаёт managed state и обнуляет static fields. Если reload отключён ради скорости, static state и события могут пережить запуск — инициализация должна быть идемпотентной, а подписки очищаться явно.

«Awake vs Start?»
Awake использую для собственной ранней инициализации объекта. Start вызывается перед первым Update у enabled-компонента и подходит, когда все scene Awake уже прошли. Но зависимость от относительного порядка разных объектов лучше выражать явной orchestration, а не надеяться на callbacks.
04

GameObject, pooling и сцены

Стоимость создания, ownership и scene lifetime.

Instantiate/Destroy — не просто выделение/удаление памяти: клонируется hierarchy, создаются native/managed части, сериализованные поля, callbacks и регистрация в подсистемах. Pooling полезен для частых повторных объектов, но требует строгого reset-контракта.

Что стоит за Instantiate

Clone hierarchy→Native + managed objects→Awake / OnEnable→Physics / Render registration

Стоимость зависит от количества компонентов, глубины hierarchy, callbacks, mesh/material/animator/physics и последующих перестроений Canvas/layout. Поэтому не утверждаем, что Instantiate «всегда дорогой» — измеряем конкретный prefab на целевой платформе.

Контракт хорошего pool

  1. Get: получить неактивный или создать в пределах capacity.
  2. OnRent: назначить зависимости и стартовое состояние.
  3. Use: владелец знает, кто и когда возвращает.
  4. OnReturn: отменить async, отписаться, остановить particles/audio, очистить ссылки.
  5. Guard: обнаружить double release.
  6. Eviction: при необходимости уменьшать pool после пика.
public interface IPoolable
{
    void OnRent();
    void OnReturn();
}

// Pooling без reset превращает старое состояние в трудноуловимый баг.
Pool может увеличить baseline memory, удерживать тяжёлые assets и усложнить lifetime. Для редких объектов он зачастую хуже обычного Instantiate/Destroy.

Сцены

  • LoadScene блокирует; LoadSceneAsync распределяет часть работы, но активация сцены всё равно может дать spike.
  • Additive loading позволяет держать bootstrap/services и менять content scenes.
  • Active scene влияет на то, куда попадают новые GameObjects и какие settings сцены активны.
  • DontDestroyOnLoad сохраняет объект между single scene loads, но легко создаёт дубликаты и «вечные» зависимости.
  • Unload scene уничтожает её GameObjects, но asset memory может оставаться из-за ссылок, Addressables handles или общей зависимости bundle.

Bootstrap architecture

Bootstrap Scene
App scope→Loading Scene→Gameplay Scene
Scene scope

App scope

Analytics, network, save, audio, global navigation. Живут всё приложение.

Level rules, scene UI, enemies, camera. Уничтожаются вместе со сценой.

Безопасная смена сцены

Запретить новые операции→Cancel / Dispose scene scope→Unload→Load + Compose

Критически важно, чтобы async-continuations и подписки старой сцены не обращались к уничтоженным объектам. Отмена должна начаться до физического unload, а не надеяться только на поздний OnDestroy.

«Как организовать Bootstrap + gameplay scenes?»
Bootstrap содержит composition root и долгоживущие сервисы. Gameplay загружаю additive, создаю отдельный scene scope, явно инициализирую его, а при переходе сначала закрываю входящие события, отменяю задачи и dispose scope, затем unload. Так lifetime виден из архитектуры, а не спрятан в DontDestroyOnLoad.
05

Architecture

SOLID, DI, Zenject, patterns и границы ответственности.

Архитектура — это управление изменениями. Хорошее решение делает вероятные изменения локальными, lifetime явным, зависимости направленными и код проверяемым. Паттерн — инструмент, а не цель.

Dependency Injection

DI — передача зависимостей снаружи. Container автоматизирует composition, но сам принцип не требует контейнера.

public sealed class CombatService
{
    private readonly ITargetProvider _targets;
    private readonly IDamageCalculator _damage;

    public CombatService(ITargetProvider targets, IDamageCalculator damage)
    { _targets = targets; _damage = damage; }
}

Constructor injection

Минимальная FSM

interface IState { void Enter(); void Tick(); void Exit(); }

{

    _current.Enter();
}
«Как понять, что архитектура переусложнена?»

UniTask и R3

Асинхронность, отмена, reactive composition и lifetime.

Асинхронная операция должна иметь владельца, срок жизни, политику отмены и обработку ошибки. Reactive pipeline должен явно описывать источник, transformation, момент переключения и disposal.

Почему UniTask подходит Unity

UniTask — task-like struct, интегрированный с PlayerLoop. Он позволяет ожидать Unity operations и frame timings, обычно с меньшими allocations, чем стандартный Task. Он не «делает код многопоточным»: большинство continuations остаётся в Unity loop.

Lifetime-safe async

private async UniTaskVoid LoadAsync(string key)
{
    var token = destroyCancellationToken; // Unity 2022.2+
    try
    {
        var result = await _loader.LoadAsync(key, token);
        token.ThrowIfCancellationRequested();
        Render(result);
    }
    catch (OperationCanceledException) when (token.IsCancellationRequested) { }
    catch (Exception e) { _logger.Error(e); }
}
GetCancellationTokenOnDestroy() связывает операцию с уничтожением объекта. Но если работа должна останавливаться уже при OnDisable, нужен отдельный CTS, который создаётся при enable и отменяется при disable.

Forget и исключения

.Forget() означает «намеренно не await». Это не право забыть об ошибке. Обработай исключение внутри или передай callback/logging policy. UniTaskVoid полезен для fire-and-forget entry point, но основную композицию лучше возвращать как UniTask.

Когда WhenAll

Load config↘WhenAll→Compose screenLoad avatar↗

Используй параллельный запуск только для независимых операций. Если B требует результат A, последовательность честнее. Продумай partial failure и release уже загруженных ресурсов.

Subject и ReactiveProperty

  • Subject — imperative bridge. Не делай его глобальной шиной для всего проекта.
  • ReactiveProperty хранит текущее значение и сигнализирует изменения.
  • Производное состояние лучше вычислять из source state, а не синхронизировать вручную несколько mutable fields.
  • Границы side effects должны быть видны: обычно в конечном Subscribe.

Когда reactive ухудшает код

Когда простой последовательный алгоритм превращается в длинную сеть операторов; ownership подписки неясен; ошибки/завершение игнорируются; Subjects используются как глобальный event bus; debugging требует угадывать невидимый flow. Тогда обычный method call/state machine может быть яснее.

«Switch или Merge?»
Merge сохраняет все inner subscriptions и отдаёт результаты каждого — подходит, когда все операции значимы. Switch отписывается от предыдущего inner при новом значении — подходит для поиска, выбранного объекта или screen state, где устаревший результат не должен попасть в UI.

Addressables и ресурсы

Catalog, bundles, handles, reference counting и memory lifetime.

Addressables решает адресацию, зависимости, загрузку и reference counting поверх AssetBundles. Главный контракт: каждая успешная load/instantiate operation имеет симметричный release соответствующим способом.

Полная цепочка

Address / Label→Catalog location→Bundle + dependencies→Asset / Instance
  • Address — ключ, а не путь к файлу на диске.
  • Catalog сопоставляет ключи resource locations и знает providers/dependencies.
  • AssetBundle — контейнер сериализованных assets; зависимые assets могут находиться в других bundles.
  • AsyncOperationHandle — наблюдение за операцией и участие в reference count.

Load vs Instantiate

ОперацияРезультатОсвобождение
LoadAssetAsync<T>Загруженный assetAddressables.Release(handle/asset)
InstantiateAsyncСозданный GameObject instanceAddressables.ReleaseInstance(instance/handle)
LoadSceneAsyncSceneInstanceUnloadSceneAsync
DownloadDependenciesAsyncФайлы в cacheHandle release; cache живёт отдельно
AsyncOperationHandle<Texture2D> handle;

async UniTask Load(string key)
{
    handle = Addressables.LoadAssetAsync<Texture2D>(key);
    var texture = await handle.ToUniTask();
    _image.texture = texture;
}

void Dispose()
{
    _image.texture = null;       // убрать consumer reference
    if (handle.IsValid()) Addressables.Release(handle);
}

Почему Release не гарантирует мгновенное падение RAM

  1. Reference count зависимости ещё больше нуля.
  2. Asset удерживается полем, UI, material, instance или static cache.
  3. Весь AssetBundle может оставаться из-за другого asset.
  4. Освобождённая память остаётся в reserved pool Unity для повторного использования.
  5. ОС/драйвер/GPU могут показать изменение позже.
  6. Скачанный bundle cache на диске — не то же самое, что runtime memory.
Release уменьшает владение, а не обещает немедленно вернуть байты ОС. Проверяй reference chain и memory snapshot.

Bundle layout и дублирование

Если общий материал/texture попал в несколько независимых bundles как неявная dependency, он может дублироваться в build/cache/memory. Если сделать один огромный shared bundle, маленький asset может удерживать всё содержимое. Layout — компромисс между гранулярностью, числом запросов, patch size и memory.

150 текстур: безопасная стратегия

Metadata / thumbnails→Окно видимых 5–15→LRU cache→Release за budget
  1. Оценить GPU size: width × height × bytes/block + mipmaps, а не размер PNG на диске.
  2. Разделить thumbnail и full-resolution.
  3. Загружать ограниченными batches/concurrency.
  4. Держать только видимое окно и небольшой cache.
  5. Явно убрать ссылки consumer перед release.
  6. Выбрать platform compression и max size.
  7. Проверить Memory Profiler в build на устройстве.

Remote content

  • Versioned catalog связывает logical address с конкретным content hash.
  • Перед download можно узнать размер зависимостей и проверить место/сеть.
  • Нужны retry с backoff, progress, cancellation и понятный fallback.
  • Catalog update во время загруженных старых bundles требует аккуратной стратегии совместимости.
  • Cache cleanup должен отличать устаревшие версии от ресурсов текущего сеанса.
«Почему asset не выгрузился после Release?»
Release уменьшает reference count операции. Я проверю другие handles и экземпляры, ссылки компонентов/static cache, общие bundle dependencies и разницу между used/reserved memory. Затем сравню Memory Profiler snapshots после контролируемого сценария, а не буду судить только по системной RAM.

Performance

CPU, GPU, memory и дисциплина измерений.

Оптимизация начинается с воспроизводимого сценария и frame budget. Сначала определить ограничивающий ресурс — main thread, render thread, GPU, memory/GC, I/O или thermal — затем найти marker, изменить одну гипотезу и повторить измерение.

CPU-bound vs GPU-bound

  • Если CPU ждёт GPU/present и снижение resolution заметно помогает — вероятен GPU bottleneck.
  • Если GPU имеет запас, а main/render thread превышает budget — CPU bottleneck.
  • VSync/frame cap могут маскировать реальную загрузку.
  • Смотри timeline и platform GPU timing, а не один FPS.

GetComponent — не универсальный злодей. В hot loop его можно cache, но сначала проверь долю в кадре. Нередко настоящая проблема — алгоритм O(n²), physics или UI rebuild.

GPU hotspots

  • Vertex-bound: много вершин/skin deformation → LOD, culling, simpler meshes.
  • Fragment/fill-bound: high resolution, overdraw, тяжёлый shader → resolution scale, opaque ordering, simplify fragment work.
  • Bandwidth-bound: большие render targets/textures, многочисленные passes → форматы, resolution, pass count.
  • Draw-call/CPU submission bound: слишком много states/objects → SRP Batcher, instancing, static batching, разумное объединение.

Memory leak или high-water mark?

Leak — память/объекты продолжают расти после повторяемого цикла и не возвращаются к устойчивому плато. High-water mark — allocator расширил reserved pool до пика и переиспользует его. Сравни snapshots после одинаковой точки и нескольких циклов.

«FPS упал с 60 до 25 — что делать?»
Фиксирую устройство, build и reproduction; записываю timeline без Deep Profile; определяю CPU/GPU/thermal; нахожу конкретный marker или pass; строю гипотезу; меняю один фактор; сравниваю captures и проверяю качество/другие устройства. Без измерения я не называю причину.

Rendering

GPU pipeline, batching, transparency, textures и RenderTexture.

CPU подготавливает и отправляет команды; GPU обрабатывает вершины, собирает примитивы, растеризует их и запускает fragment shader для потенциальных пикселей. Bottleneck определяется количеством работы на конкретной стадии, а не просто «числом полигонов».

Упрощённый pipeline

CPU culling + commands→Vertex shader→Rasterization→Fragment shader→Framebuffer

Draw call и SetPass

Draw call — команда нарисовать геометрию. SetPass/state change — смена pipeline/material state и часто более значимый CPU overhead. Число draw calls — индикатор, не универсальная цель.

ТехникаКогда помогаетЦена/ограничение
SRP BatcherМного материалов с совместимыми SRP shadersТребует правильного layout shader properties
GPU InstancingОдин mesh/material, много экземпляровРазличия передаются instance data; не любой shader
Static BatchingНеподвижная геометрияДополнительная memory, хуже при динамике
Dynamic batchingМелкие совместимые meshesОграничения; CPU transformation может не окупиться

Depth, transparency и overdraw

Opaque objects обычно могут использовать depth test/write и отбрасывать скрытые fragments. Transparent объекты часто рисуются back-to-front, не пишут depth привычным способом и многократно обрабатывают один пиксель.

Пиксель фона+Particle 1+Particle 2+UI overlay= overdraw
На mobile большой полупрозрачный quad может быть дороже сложной маленькой mesh: платим за число fragments × площадь экрана × passes.

Textures

  • Mipmaps уменьшают aliasing и texture sampling cost вдали, но добавляют примерно треть памяти к полной mip chain.
  • Filtering: bilinear берёт соседние texels, trilinear смешивает mip levels, anisotropic улучшает наклонные поверхности ценой выборок.
  • Compression: выбирается по platform/GPU; размер файла PNG/JPG не равен GPU memory.
  • sRGB vs Linear: color textures обычно sRGB, data maps — linear.

RenderTexture: модель lifetime

Descriptor→ CreateGPU resource→ BindCamera / Pass writes→Consumer samples

Почему может стать чёрной

  1. Resource не создан, потерян или released.
  2. Camera отключена, culling mask пуст, target переназначен.
  3. Неверный порядок: consumer читает до producer.
  4. Descriptor/format/MSAA несовместимы с platform.
  5. Temporary RT использован после release или за пределом frame lifetime.
  6. Shader stripped/keyword отличается в build.
  7. Texture потеряла содержимое при background/context loss; нужно проверить IsCreated и пересоздать.
  8. UI material/alpha/color space выдаёт визуально чёрный/прозрачный результат.

План диагностики build-only RenderTexture

  1. Минимальный prefab и Development Build.
  2. Логировать descriptor, IsCreated, camera enabled/targetTexture в момент сбоя.
  3. Принудительный known-color clear, затем простой unlit consumer.
  4. Frame Debugger / RenderDoc: был ли pass и что записано.
  5. Убрать MSAA/HDR, взять поддерживаемый format.
  6. Проверить app pause/resume и пересоздание GPU resource.
  7. Сравнить Graphics API, stripping, device/driver.
«Как уменьшить draw calls?»
Сначала подтверждаю CPU submission bottleneck. Затем уменьшаю лишние material variants/state changes, использую SRP Batcher, instancing или batching под подходящую геометрию, culling/LOD и объединение UI. После каждой меры проверяю CPU и GPU: меньше draw calls не гарантирует быстрее.

Mobile: Android и iOS

Build pipeline, native boundaries, memory, thermals и device lifecycle.

Мобильная разработка — это работа с неоднородным железом, ограниченным memory/thermal budget и жизненным циклом ОС. Проверять нужно development build на реальных устройствах, включая background/restore и слабый network.

Android build pipeline

C# assemblies→ IL2CPPC++→ NDKARM native libs→ GradleAPK / AAB
  • APK — устанавливаемый пакет; AAB — publishing format, из которого Google Play формирует device-specific APKs.
  • Gradle собирает Android project и зависимости.
  • AndroidManifest описывает components, permissions, intent filters и metadata.
  • Activity — Android UI/lifecycle host Unity player.
  • ARM64 — целевая ABI; native plugins должны содержать совместимые binaries.
  • JNI — граница Java/Kotlin ↔ native; важны main/UI thread, lifetime local/global refs и стоимость частых вызовов.

iOS build pipeline

Unity project→ IL2CPPXcode project→ signingApp / archive
  • Bundle identifier + certificate + provisioning profile должны согласовываться.
  • Info.plist содержит usage descriptions, URL schemes и настройки приложения.
  • Native plugins подключаются к Xcode target; C# boundary обычно проходит через P/Invoke / generated bindings.
  • AOT/IL2CPP ограничивает runtime code generation и требует внимания к reflection/generic stripping.

IL2CPP и code stripping

IL2CPP преобразует IL в C++, затем platform compiler создаёт native binary. Это AOT, поэтому конструкции, создаваемые только через reflection, serializer или generic runtime path, могут быть не видны static analysis.

Симптом

В Editor работает, в IL2CPP build отсутствует тип, метод или serializer fails.

Проверка

Development IL2CPP build, managed stripping level, logs, generated/linker reports.

Решение

[Preserve], link.xml, явная reference/registration, supported serializer path.

Не делать

Не отключать stripping глобально как вечное решение без оценки размера и причины.

Memory budget

Следи не только за managed heap. Основные потребители: textures, meshes, audio, animation, render targets, native engine objects, managed state и plugins.

Texture compression

  • ASTC поддерживает разные block sizes: меньший block → выше качество и размер.
  • ETC2 — распространённый fallback для совместимых Android devices.
  • iOS поддерживает ASTC/PVRTC/ETC2 в зависимости от device target; DXT не является iOS native format.
  • Используй platform overrides и проверяй реальное качество на устройстве.

Thermal throttling

Высокая CPU/GPU load→Нагрев→Снижение частот→FPS падает через 10–20 мин

Короткий benchmark может выглядеть идеально. Делай sustained test, отслеживай temperature/clock/power косвенно platform tools, сравнивай FPS и frame time во времени. Dynamic resolution, frame cap и quality tiers могут быть лучше постоянной максимальной нагрузки.

Lifecycle: pause, focus, termination

  • Сохраняй критическое состояние при уходе в background, а не только при quit: ОС может завершить процесс.
  • Останавливай timers, camera/mic, network heartbeat и тяжёлый rendering по политике продукта.
  • После resume перепроверяй auth, connectivity, elapsed real time и GPU resources.
  • Не рассчитывай, что OnApplicationQuit гарантирован на mobile.

Safe Area и ориентация

Реагируй не только на resolution, но и на safe area/orientation change. Преобразуй pixel rect в anchors или рассчитанные offsets относительно текущего canvas; кэшируй последнее состояние и перестраивай UI только при изменении.

Кейс: Android падает через 20 минут

  1. Сегментировать: модель, OS, RAM, GPU, graphics API, thermal state.
  2. Получить logcat/crash/ANR и точный момент.
  3. Построить граф managed/native/GPU memory и object counts.
  4. Повторить фиксированный игровой цикл; snapshots после каждого круга.
  5. Отделить OOM от native crash, watchdog/ANR и thermal slowdown.
  6. Проверить texture format, bundles, pools, native plugins, background/resume.
  7. Исправить и провести долгий soak test на том же слабом устройстве.
«Почему Editor не показывает mobile-проблему?»
Отличаются backend, stripping, Graphics API/driver, architecture, файловая система, permissions, memory/thermal budget и lifecycle ОС. Я воспроизвожу в Development IL2CPP build на проблемном устройстве и использую platform logs/profilers.

Jobs, Burst и ECS

Параллельность, data layout и выбор правильного масштаба.

Job System планирует безопасную параллельную работу над native data; Burst компилирует совместимый C# в оптимизированный native code; ECS организует данные по компонентам для массовой обработки. Они дополняют друг друга, но решают разные задачи.

Три разных инструмента

ИнструментЧто решаетНе гарантирует
Job SystemScheduling и зависимости worker jobsАвтоматическое ускорение любой маленькой работы
BurstОптимизированный native machine codeПоддержку всего managed C# и Unity API
ECSData-oriented layout и systems over queriesПростоту authoring для любой игры

Job dependency

Read input
Job A→ handleWrite result
Job B→ CompleteMain thread consumes

Schedule() не означает, что job уже завершён. JobHandle описывает зависимость. Слишком ранний Complete() превращает parallel work в main-thread stall; слишком поздний — consumer читает недоступные данные.

Race conditions и safety

Две jobs могут параллельно читать одинаковые данные. Если хотя бы одна пишет, нужна dependency или безопасное partitioning. Safety system обнаруживает многие нарушения доступа в development/editor, но архитектуру владения данными всё равно проектирует разработчик.

Native containers и allocators

AllocatorОжидаемый lifetimeПравило
TempОчень короткий, обычно один frameСамый быстрый, не передавать в долгие jobs
TempJobНесколько framesДля scheduled work, своевременно Dispose
PersistentДолгоживущийЯвное владение и Dispose обязательны

NativeArray — фиксированный буфер; NativeList меняет длину. Оба используют unmanaged/native allocation, поэтому GC их не освободит как обычный managed object.

Burst-friendly code

  • Данные в blittable/unmanaged structures.
  • Минимум managed references, virtual dispatch и exceptions.
  • Чистая математика, простые loops, предсказуемый memory access.
  • Проверять Burst Inspector и реальный profiler, не полагаться только на «Burst enabled».

ECS: Entity + Component + System

Entity
identifier+Components
data→Archetype / chunks←System
logic
  • Entity — идентификатор, не объект с behaviour.
  • IComponentData — данные; лучше небольшие и ориентированные на query/use.
  • Archetype — уникальный набор component types.
  • Chunk хранит entities одного archetype плотно, что улучшает locality.
  • System выбирает entities по components и трансформирует данные.
  • Structural change меняет archetype (добавление/удаление component/entity) и может перемещать данные; часто буферизуется через ECB.

Почему data-oriented бывает быстрее

Нужные PositionрядомCache lines→SIMD / Jobs→Mass update

В OOP-графе данные, нужные системе, могут быть разбросаны по объектам вместе с ненужными полями и ссылками. ECS группирует одинаковые компоненты и делает pattern чтения/записи явным.

Когда ECS не нужен

  • Мало entities и нет измеренного массового bottleneck.
  • Основная сложность — уникальное object-oriented behaviour, UI или authoring.
  • Команда не владеет DOTS tooling/debugging.
  • Цена hybrid integration превышает выигрыш.
  • Feature меняется быстрее, чем стабилизируется data model.
«Почему ECS не использовать везде?»
ECS выигрывает на массовой однотипной обработке и data locality, но добавляет стоимость authoring, structural changes, debugging и интеграции с GameObject-миром. Я выбираю его по профилю нагрузки; часто лучший вариант — hybrid: high-level presentation на GameObjects, тяжёлые массовые simulations в DOTS.

Networking, persistence и testing

Надёжные внешние границы и проверяемый код.

Сеть ненадёжна, сохранения переживают версии, тесты должны защищать важное поведение. На внешних границах проектируй timeout, cancellation, versioning, retry policy и наблюдаемость.

HTTP, WebSocket, TCP и UDP

ТехнологияСильная сторонаТипичный сценарий
HTTP/RESTRequest/response, инфраструктура, cachingauth, inventory API, config
WebSocketДолгое двустороннее соединениеchat, live updates, lobby
TCPНадёжный упорядоченный byte streamкогда потеря недопустима
UDPDatagrams без встроенной доставки/порядкаlatency-sensitive realtime protocol
TCP не «медленный», UDP не «быстрый по умолчанию». Выбирают модель доставки. Надёжность, ordering, congestion control и security для UDP приходится проектировать поверх него или брать готовый transport.

Надёжный request

Validate→Timeout + token→Send→Classify result→Retry or surface
  • Retry только для transient failures и с exponential backoff + jitter.
  • Не повторяй неидемпотентную оплату/покупку без idempotency key.
  • Разделяй transport error, HTTP status, domain error и malformed payload.
  • Refresh token request должен быть single-flight: параллельные 401 не запускают десять refresh.
  • Логи содержат correlation id и timing, но не токены/PII.

Serialization

JSON

Читаем, гибок, удобен для API/debugging. Больше размер и parse cost.

Binary

Компактнее/быстрее при хорошей схеме. Сложнее inspect и version.

Не сериализуй domain objects «как есть» навсегда. DTO/schema — контракт границы. Валидируй ranges, отсутствующие поля и неизвестные версии.

Save system

Runtime modelmapSave DTO + versionserializeTemp fileatomic replaceMain save
  • PlayerPrefs — маленькие preferences, не защищённая база и не большие saves.
  • Пиши во временный файл, flush/close, затем atomic replace где возможно.
  • Держи backup предыдущего успешного save.
  • Храни schemaVersion и цепочку migrations v1 → v2 → v3.
  • Cloud save требует conflict policy: timestamps недостаточно, полезны revisions/vector/domain merge.
  • Шифрование клиента не делает данные доверенными: ключ и код находятся у пользователя.

Хороший тест

  • Проверяет observable behaviour, а не приватную реализацию.
  • Детерминирован: контролирует clock, random, network и filesystem.
  • Имеет ясные Arrange → Act → Assert.
  • Падает по одной понятной причине.
  • Не требует mock каждого класса: fakes и реальные value objects часто проще.
«Что тестировать в Unity-проекте?»
Максимально выношу domain logic в обычный C# и покрываю unit tests. Интеграционными тестами проверяю adapters и composition, PlayMode оставляю для lifecycle/scene/physics поведения, а ключевые platform flows запускаю на device. Уровень выбираю по риску и стоимости обратной связи.

Senior System Design

Как проектировать вслух и показывать инженерное мышление.

Не начинай с классов. Сначала уточни требования, масштаб, consistency и ограничения; затем определи данные, ownership, API и flows; после — failures, observability и trade-offs.

Универсальный алгоритм

  1. Clarify: пользователи, platform, online/offline, объём, latency, consistency.
  2. Scope: что проектируем сейчас и что оставляем вне рамок.
  3. Invariants: правила, которые нельзя нарушить.
  4. Data: definitions, runtime instances, identity, persistence.
  5. Ownership/lifetime: кто создаёт, изменяет и уничтожает.
  6. API и main flows: happy path до деталей.
  7. Failures: cancellation, retries, partial completion, recovery.
  8. Scale/performance: budgets, batching, cache, concurrency.
  9. Observability/tests: как докажем корректность.
  10. Trade-offs: альтернативы и причина выбора.
Запоминалка: R–D–F–F–S: Requirements → Data → Flows → Failures → Scale.

Inventory

ItemDefinition
immutable config→ idItemInstance
runtime identity/state→Slot / Stack→Inventory aggregate

Инварианты

  • Количество не отрицательно и не превышает stack limit.
  • Unique item с instance state не сливается как обычный stack.
  • Transfer атомарен: либо item ушёл из A и пришёл в B, либо ничего.
  • UI не владеет inventory state, а отображает изменения.

Дизайн

ItemDefinition можно хранить в ScriptableObject/remote config, но save содержит stable definition id, количество и instance state. InventoryService выполняет команды и выдаёт события/readonly state. Persistence сохраняет DTO, а UI подписывается на change set.

Quest system

Quest Definition→Quest ProgresslistensDomain Events→Reward transaction
  • Definition отделена от player progress.
  • Objectives получают типизированные domain events, а не опрашивают весь мир каждый frame.
  • Reward idempotent: повторная доставка события не выдаёт награду дважды.
  • Версии контента требуют policy для изменившихся/удалённых quests.

UI framework

Navigation request→Router / stack→Factory async load→View + Presenter
  • Разделить Screen, Popup, Overlay; определить правила back.
  • Один owner навигационной stack предотвращает конфликт переходов.
  • Операции открытия сериализуются или имеют version/cancellation.
  • View не содержит business state; Presenter/ViewModel имеет ясный scope.
  • Переход владеет loaded handle и освобождает его после закрытия/кэширования.

Remote Addressables

Check catalog→Compatibility + size→Download staged→Verify / activate→Fallback

Нужно продумать: обязательный/опциональный update, minimum app version, свободное место, metered network, resume, hashes, cache cleanup, rollback и telemetry по стадиям.

10 000 NPC

Сначала уточнить, сколько одновременно видимы, имеют физику/анимацию/AI и насколько точной должна быть симуляция.

СлойПодход

Как говорить во время system design

  • Озвучивай предположения: «Если inventory только локальный…; если authoritative server — контракт меняется».
  • Сначала baseline, затем evolution path.
  • Не скрывай неопределённость: предложи измерение или spike.
  • Привязывай решения к ограничениям, не к личной любви к паттерну.
Шаблон финала:
Я выбрал этот вариант, потому что главные constraints — X и Y. Он обеспечивает такие invariants и локализует изменения здесь. Цена — A и B. При росте до Z я бы вынес/заменил такую часть. Проверю решение тестами, profiler budget и telemetry.

Mock Interview и финальная шпаргалка

Готовые структуры ответов и контрольные вопросы.

На mock interview не перечитывай материал между вопросами. Запиши ответы, ограничь время, а затем оцени: корректность механизма, ясность, пример, trade-offs и проверку.

Структура ответа на 90 секунд

1. Определение
10–15 сек→2. Механизм
25 сек→3. Unity-пример
25 сек→4. Trade-off
20 сек

Раунд 1 — C#

Class vs struct?

Семантика ссылки/значения, копирование, identity, placement caveat, размер/mutability.

Что такое boxing?

Value → object/interface, heap allocation + copy; назвать реальный источник.

Как работает Dictionary?

Hash → bucket → equality; average O(1), collisions, mutable key.

Closure?

Захват внешнего state, compiler-generated storage, lifetime/allocation.

Как работает GC Unity?

Roots/reachability, non-generational/non-compacting, incremental slices.

async/await?

State machine/continuation; не обязательно thread; errors/cancellation.

Раунд 2 — Unity

Awake vs Start?

Собственная ранняя init vs перед первым Update; не строить hidden order.

FixedUpdate?

Fixed simulation step; 0/1/many раз на render frame.

Unity fake null?

Managed wrapper и уничтоженный native object; overloaded equality.

Addressables Release?

Reference count; не обещает мгновенный возврат RAM.

CPU или GPU?

Frame timing, waits, resolution experiment, target device profiler.

Чёрная RenderTexture?

Producer/order/lifetime/format/context/shader stripping/consumer.

Раунд 3 — Architecture

  1. Спроектируй систему окон с back stack и async Addressables.
  2. Спроектируй inventory с unique items, stacking и save migration.
  3. Определи app/scene/object scopes в DI.
  4. Объясни, когда события лучше прямого вызова и когда хуже.
  5. Покажи evolution простой FSM при росте переходов.

Раунд 4 — Debugging

Красные флаги в ответах

  • «Всегда» и «никогда» без контекста.
  • Оптимизация до profiler.
  • Паттерн как ответ без требования, которое он решает.
  • Игнорирование cancellation, failure и cleanup.
  • Смешение managed, native, GPU и disk memory.
  • Глобальные singleton/event bus как default.
  • «Работает в Editor» как достаточная проверка.

Финальная ультракороткая шпаргалка

C#: value/reference — семантика; boxing allocates; closure захватывает state; Dictionary зависит от hash + equality.
GC: roots → reachability; incremental дробит marking; native resources требуют своего release.
Unity: PlayerLoop важнее списка callbacks; FixedUpdate 0/1/N; порядок делай явным.
Async: owner + token + error + stale result policy. Await не равен thread.
R3: Merge — все; Switch — последний; subscription всегда имеет lifetime.
Addressables: load/release симметричны; handle — ownership; RAM может не упасть сразу.
Performance: reproduction → profiler → bottleneck → one change → compare.
Rendering: CPU submission, vertex, fragment, bandwidth; прозрачность = overdraw.
Mobile: IL2CPP, stripping, memory, thermal, lifecycle и реальные devices.
DOTS: Jobs schedule, Burst compiles, ECS lays out data. Использовать по профилю.
Перед ответом сделай паузу на 2–3 секунды.
Уточнить условие и построить структуру — признак зрелости. Если не знаешь деталь API, честно отдели известный механизм от предположения и скажи, как быстро проверишь его документацией или экспериментом.
